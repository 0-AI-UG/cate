# T3 integration tests

Build the app and its host runtime, then run the integration suite:

```sh
npm run runtime:tarball
npm run build
npm run test:e2e:agent
```

After changing only app code, rebuild the app. After changing runtime code,
`npm run build:runtime` updates the daemon bundle used by these tests without
rebuilding the tarball. The tarball must still exist for runtime provisioning.

The macOS CI job builds the runtime tarball and runs this suite as a required
job step. To run only the real T3 scenarios locally:

```sh
npm run test:e2e:agent -- --grep 'real T3'
```

## Boundaries

- `fake-t3.cjs` tests Cate's Electron/webview surface, provider-login UI,
  branding, navigation restrictions, activity, keyboard focus, and detached
  panel deletion. It is not evidence of compatibility with the real T3 router.
- Tests named `real T3` use the installed, patched T3 server and web client.
  They cover native settings RPC and both new-conversation entry points.
- `real T3 lifecycle` additionally uses `fake-codex-app-server.cjs` as the
  provider executable, with an isolated provider home and settings profile.
  Before sending, setup checks that T3 selected that executable. The real T3
  database, orchestration, provider adapter, and UI handle messages, approvals,
  cancellation, provider exit, switching chats, and restore/resume after
  restarting Cate. No live model account is needed for these lifecycle tests.
- The streaming test enables T3's streaming preference and holds the final
  provider chunk until it has asserted partial output and a running turn.
  Other lifecycle tests exercise the default buffered message mode.
- Title tests exercise T3's separate Codex `exec` command, structured-output
  parsing, initial generation, regeneration, and propagation to the tab,
  action-bar list, and native overlay menu before and after restart. Invalid
  provider JSON exercises the message-title fallback and continued chatting.
- Settings tests edit custom models, ordinary and secret environment variables,
  launch arguments, account appearance, preferences, and additional accounts.
  They verify persistence across restart, unchanged redacted secrets surviving
  another save, environment deletion, and the actual provider subprocess's
  arguments, home directory, and environment. All secret values are synthetic.
- The overlay's native menu invokes its actual Electron item callback through
  a one-use `Menu.popup` override. This tests IPC and selection behavior, but
  not operating-system menu hit testing.

Provider protocol requests and guest text are attached on failure. Unknown
provider RPC methods fail explicitly; update the fixture against the pinned
T3 schema when upgrading T3, rather than replacing the real server with a mock.

`src/main/t3Agent/T3HarnessManager.test.ts` separately tests startup sharing,
canonical paths, worktree/runtime isolation, retries, shutdown, disconnects,
and sign-in ownership. Those tests mock server startup and file synchronization;
remote-host transport and packaged Windows/Linux T3 execution are not covered
by this macOS E2E gate.

Renderer unit tests additionally cover disconnected/empty titles, unrelated
threads, user-renamed panels, and a stale guest response after switching chats;
settings units cover failed saves, discard, and provider-specific field types.
These fixtures do not validate title quality from a live model or actual
third-party authentication, updates, and provider-service availability.
